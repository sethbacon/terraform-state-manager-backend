# 5. OpenAPI Spec Generated from swag Annotations

**Status**: Accepted

## Context

The project documentation (`CLAUDE.md`) described the API spec as a hand-authored **OpenAPI 3.0** document at `backend/docs/swagger.yaml`, declared the "source of truth," with a rule that every handler have a matching entry added to that YAML before commit.

Inspection of the codebase shows this is inaccurate:

- There is **no** `swagger.yaml` file. The only spec artifact is `backend/docs/swagger.json`.
- The handlers carry **swag annotations** (121 `// @Router` blocks across `internal/api`). `backend/docs/embed.go` states the file "is generated by swag from handler annotations — run `make swag` to regenerate after handler changes" and embeds it via `//go:embed swagger.json`.
- The generated spec is **Swagger 2.0**, not OpenAPI 3.0.
- The router serves the bytes at both `GET /swagger.json` (correctly) and `GET /swagger.yaml` (which returns the same JSON bytes labeled `application/yaml`).

This matches the registry backend's model (annotations + `swag init`), so aligning is also a consistency win.

## Decision

Treat the **handler swag annotations as the source of truth**. `backend/docs/swagger.json` (Swagger 2.0) is a generated, embedded artifact regenerated with swag (e.g. `make swag` / `swag init`) after handler changes; it is committed but never hand-edited. Correct the `CLAUDE.md` "API Documentation" section to describe this accurately (annotations as source, Swagger 2.0, `swagger.json` not `swagger.yaml`).

Two follow-ups are recorded, not done here:

1. Add a CI step that regenerates the spec with swag and fails on drift (as the registry's CI does), so committed `swagger.json` cannot fall out of sync with the annotations. The current CI only validates that `swagger.json` parses.
2. Fix the `/swagger.yaml` endpoint to either emit real YAML or be removed, so the content type is not misleading.

### Alternatives considered

- **Switch to a hand-authored spec** (make the docs true as written): rejected — it discards the existing annotations, diverges from the registry, and makes the spec drift from the handlers by construction.

## Consequences

**Easier**:

- The documentation now matches reality and the registry's workflow; contributors annotate handlers and regenerate, rather than editing a non-existent YAML.

**Harder**:

- Until the CI drift-check (follow-up 1) lands, keeping `swagger.json` in sync with annotations relies on contributor discipline.
- The mislabeled `/swagger.yaml` endpoint remains until follow-up 2.
